# v0.9.23 Plan Catalog And Module Entitlements Design

## Objective / 目标

Deliver one independently useful Phase 8 capability: a server-owned plan catalog and organization-level module entitlements. Existing organizations and newly created organizations retain current behavior through the `legacy_full` plan. Subscription expiry, billing, shared monthly quota, persistent concurrency reservation, and AI-plan gating remain separate releases.

交付一个可独立上线的阶段 8 能力：由服务端权威维护的套餐目录与组织级模块权益。现有组织和新建组织默认使用 `legacy_full`，保持当前行为不变。订阅到期、账单、组织月度共享配额、持久并发预留及 AI 套餐准入继续拆分上线。

## Release Cadence / 发布节奏

- One feature, one production release. The slice deploys as soon as affected verification, one independent review, a verified backup, and focused production acceptance pass.
- Ordinary features do not run unrelated heavy suites. This slice changes schema and authorization, so migration replay/integrity and focused permission regressions are mandatory risk-triggered checks.
- The latest application shell, customer screens, M3/M4 flows, AI/knowledge behavior, and frozen `ppt.js` remain unchanged.

## Authoritative Model / 权威模型

- Catalog version: `1`.
- Stable plans: `legacy_full` and `crm_core`.
- Entitlement keys are the exact organization-scoped module codes already enforced by the central module-action service:
  - `crm.customer`
  - `crm.opportunity`
  - `crm.contact`
  - `crm.task`
  - `campaign.performance`
  - `campaign.customer_report`
  - `influencer.data`
- `legacy_full` contains all seven modules. `crm_core` contains the four CRM modules.
- Plan definitions are seeded and immutable at runtime. Administrators may assign plans but cannot edit catalog definitions in this release.
- Every organization has exactly one authoritative current assignment: the append-only row with the highest unique assignment version. Prior rows remain immutable history, so the current assignment cannot disappear through an update or delete.
- Existing organizations are backfilled to `legacy_full`; an organization-insert trigger assigns `legacy_full` to new organizations.

## Authorization Contract / 授权合同

For organization-scoped module actions, the server evaluates live facts and enforces:

`role permission ∩ active organization plan entitlement`

The existing AI quota remains a separate admission layer. The future complete chain is:

`role permission ∩ plan entitlement ∩ quota`

- Browser input, JWT claims, cached UI state, and request-supplied plan/module values are never authoritative.
- Platform administration remains outside organization plan entitlements.
- If the role permits an action but the active plan does not contain the module, authorization returns `PLAN_ENTITLEMENT_REQUIRED`.
- Projection returns an empty action list for a non-entitled module so login and `/api/auth/me` remain usable.
- Missing, duplicate, inactive, or unreadable plan facts fail closed with `ENTITLEMENT_POLICY_UNAVAILABLE`.
- Plan changes take effect on the next authenticated request because authorization already reloads live facts per request.

## Data Contract / 数据合同

Migration `027_plan_catalog_module_entitlements` creates:

- `plan_catalog`: immutable catalog rows with stable code, bilingual names, version, status, and display order.
- `plan_module_entitlements`: immutable `(plan_code, module_code)` membership.
- `organization_plan_assignments`: append-only versioned assignment history with actor, reason, source, and timestamp; the highest version is current.

Database constraints and triggers enforce exact vocabularies, immutable catalog membership, contiguous assignment versions, no assignment update/delete, and automatic `legacy_full` assignment for new organizations.

## Service And API Contract / 服务与接口合同

- `GET /api/admin/plan-catalog`: active platform administrators only; returns the catalog and module entitlements.
- `GET /api/organization-entitlements`: authenticated active organization members; returns the current organization plan and entitlement projection.
- `PUT /api/admin/organizations/:organizationId/plan`: active platform administrators only; exact body `{ plan_code, expected_version, reason }`; compare-and-swap assignment and bounded audit in one immediate transaction.
- The organization governance list includes a read-only plan summary. Only platform administrators receive `assign_plan: true`.

## Audit And Failure Semantics / 审计与失败语义

- Successful plan changes append `organization_plan_assigned` to `activity_log` in the same transaction.
- The audit records actor, organization, previous and new plan, previous and new assignment version, request ID, and bounded reason.
- Audit failure rolls back the plan change.
- Stale `expected_version` returns `409 PLAN_ASSIGNMENT_VERSION_CONFLICT`.
- Assigning the current plan is an idempotent read result and does not append history or audit.

## Explicit Exclusions / 明确排除

No pricing, payment, subscription term, expiry, seat billing, self-service purchase, user-level plan override, dynamic catalog editing, organization shared quota, persistent concurrency reservation, or broad UI redesign is included.
