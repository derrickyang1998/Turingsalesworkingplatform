# v0.9.26 Durable AI Provider Concurrency Reservation / AI Provider 持久并发预留

## Goal / 目标

Add a durable organization-level concurrency boundary for external AI provider work. Every logical AI operation must acquire one database-backed permit before Tavily or DeepSeek dispatch, keep that permit across the complete provider sequence, and release it only after the operation reaches a terminal state.

为外部 AI Provider 工作增加组织级持久并发边界。每次逻辑 AI 操作必须在调用 Tavily 或 DeepSeek 前取得一个数据库持久许可，在完整 Provider 调用链期间持续持有，并在操作进入终态后才释放。

## Product Contract / 产品契约

- Each organization has an append-only concurrency policy. The default is `10`, `0` disables new AI work, and the maximum configurable value is `64`.
- One logical AI operation consumes one slot. Sequential Tavily and DeepSeek calls reuse the same reservation; completed idempotent replays consume no slot.
- Admission is fail-closed and occurs before RAG/web/provider/business-result writes. A full organization receives `429 AI_ORGANIZATION_CONCURRENCY_LIMIT_REACHED` with a bounded `Retry-After` value.
- Reservations survive process restarts. A random fencing token owns the reservation, provider work has a 120-second deadline, and abandoned work becomes reclaimable 15 seconds later.
- Lowering the limit does not terminate in-flight work. When active work exceeds the new limit the organization is `draining` and new work is rejected until capacity returns.
- Platform administrators are not exempt. Emergency capacity changes use the same versioned policy update with a required reason and a hard maximum of `64`.
- No wait queue, priority system, forced release UI, billing, provider pricing, or Token pre-charge is introduced. Monthly Token quota remains the independent settled-usage boundary from v0.9.25.
- Scope includes actual Tavily/DeepSeek operations used by brand enrichment, strategy, demand/proposal/PPT-outline AI, chat, and performance AI analysis. CRM, imports/exports, parsers, knowledge CRUD/search, Feishu sync, and local PPTX rendering do not consume slots.

- 每个组织具有只追加的并发策略；默认值为 `10`，`0` 表示停止新 AI 工作，可配置最大值为 `64`。
- 一次逻辑 AI 操作占用一个槽位；顺序执行的 Tavily 与 DeepSeek 复用同一预留，已完成幂等重放不占槽位。
- 准入采用失败关闭，并发生在 RAG、联网、Provider 和业务结果写入之前。组织满载时返回 `429 AI_ORGANIZATION_CONCURRENCY_LIMIT_REACHED` 及有界 `Retry-After`。
- 预留跨进程重启保留；随机 fencing token 标识所有权，Provider 工作截止时间为 120 秒，15 秒后可回收遗留工作。
- 下调上限不终止在途工作；活跃数高于新上限时状态为 `draining`，容量恢复前拒绝新请求。
- 平台管理员不绕过并发上限；紧急扩容仍通过带原因与版本校验的策略变更完成，硬上限为 `64`。
- 本版本不引入等待队列、优先级、强制释放界面、账单、Provider 定价或 Token 预扣。月度 Token 额度继续使用 v0.9.25 的独立已结算用量边界。
- 覆盖品牌增强、策略、需求/方案/PPT 大纲 AI、对话和效果复盘 AI 等真实 Tavily/DeepSeek 操作；CRM、导入导出、解析器、知识库 CRUD/搜索、飞书同步和本地 PPTX 渲染不占槽位。

## Data And API / 数据与接口

- Schema v30 adds immutable `organization_ai_concurrency_policies`, durable `ai_provider_reservations`, and append-only `ai_provider_reservation_events`.
- Reservation states are `active -> released | timed_out`; identity fields are immutable and a stale fencing token cannot authorize dispatch or release another worker's reservation.
- `GET /api/organization-ai-concurrency` returns the current member's aggregate projection.
- `PUT /api/admin/organizations/:organizationId/ai-concurrency` accepts exactly `concurrency_limit`, `expected_version`, and `reason`.
- Organization directory projections add `ai_concurrency` with `active`, `limit`, `available`, `over_capacity`, `status`, `policy_version`, and `earliest_lease_expires_at`.
- Status values are `available`, `full`, `draining`, `disabled`, and `unavailable`.
- Event and activity logs contain bounded metadata only; prompts, model responses, API keys, cookies, and raw fencing tokens are never logged.

## Correctness Invariants / 正确性不变量

1. At every acquire linearization point, active reservations for an organization do not exceed the effective limit.
2. No valid persisted permit and dispatch authorization means zero external provider calls.
3. Network I/O never runs inside a SQLite transaction.
4. Reservation identity is immutable, terminal states cannot return to active, and stale owners cannot settle or release.
5. Completed idempotent replay performs no new reservation or provider call.
6. Concurrency rejection creates no Token usage, AI response, proposal/PPT output, knowledge entry, or web-search cache result.
7. Decreasing a policy below active work drains safely without cancelling accepted requests.

## Reversible Production Acceptance / 可逆线上验收

1. Upgrade a production-shaped sanitized copy from v29 to v30 twice and verify schema history, integrity, foreign keys, policy backfill, and unchanged historical Token usage.
2. Record one acceptance organization's current policy, append a temporary limit of `1`, and acquire one root-only test reservation.
3. Send a second uniquely tagged request and prove it returns `AI_ORGANIZATION_CONCURRENCY_LIMIT_REACHED` before provider dispatch or business writes.
4. Release the held reservation, run one controlled request, and verify reservation/event terminal closure and Token accounting where a Provider succeeds.
5. Restore the original policy through the next version, prove active reservations are `0`, retain bounded audit evidence, and remove only temporary authentication/test artifacts.
6. Any mandatory failure triggers the recorded database and code rollback before public traffic resumes.

## Release Boundary / 发布边界

Included: schema v30, reservation service, Provider admission boundary, member/admin APIs, compact Admin organization controls, aggregate status projection, focused migration/concurrency/permission/API/UI/provider-inventory tests, backup, production deployment, and reversible online acceptance.

Excluded: precise Token reservation, billing, queues, priority, distributed workers, local PPT render concurrency, generic task center, provider-cost conversion, and historical concurrency charts.
