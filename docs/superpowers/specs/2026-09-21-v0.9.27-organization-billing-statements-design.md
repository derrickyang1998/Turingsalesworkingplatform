# v0.9.27 Organization Billing Policy And Monthly Statements / 组织计费策略与月度账单

## Goal / 目标

Add a bounded SaaS billing control for organization AI usage. Administrators can configure a next-month-or-later USD policy, owners and organization administrators can inspect their own monthly estimate, and platform administrators can close an ended UTC month into one immutable, reproducible statement.

为组织 AI 用量增加边界清晰的 SaaS 账单控制。平台管理员可配置最早下一个 UTC 月生效的美元计费策略，企业所有者和组织管理员可查看本组织月度预估，平台管理员可将已结束的 UTC 月份结算为一份不可变且可复算的账单。

## Product Contract / 产品契约

- Every organization has append-only billing policy history. Existing and new organizations default to billing disabled with zero base fee, zero included Tokens, and zero overage rate; this release never invents a commercial price.
- A policy contains `billing_enabled`, `base_fee_cents`, `included_tokens`, `overage_cents_per_million_tokens`, `currency=USD`, an effective UTC month, and a monotonically increasing version.
- Platform administrators may append a policy only for the next or a later UTC month, using optimistic version checks and a required reason. Current-month and retroactive repricing are rejected.
- Monthly usage comes only from the immutable, organization-owned `token_usage` ledger. Every organization-owned row is billable in v1, including usage created by a platform administrator while acting inside that organization. The estimate never trusts browser totals or mutable conversation content.
- The v1 formula is `billable_tokens=max(total_tokens-included_tokens,0)`, `overage_fee_cents=round_half_up(billable_tokens*rate/1,000,000)`, and `total_cents=base_fee_cents+overage_fee_cents`. All arithmetic is integer-safe and the formula version is persisted.
- Billing-disabled months return a zero estimate and cannot be closed. The current month is an estimate, a future month is scheduled, and an ended month can be closed once. v1 does not prorate partial months. Closing is idempotent for an identical request and conflicts when the expected effective policy version or stored digest differs.
- Statements snapshot usage, policy, formula, actor, reason, period boundaries, and a SHA-256 digest. They are append-only and cannot be updated, deleted, replaced, or recomputed in place.
- Usage appended after closure never mutates or replaces the closed statement. A later policy version changes `policy_head_version` but not the statement's persisted effective `policy_version`.
- Company owners and organization administrators can read only their own organization. Platform administrators can read any organization, update policies, and close statements. Managers, members, read-only users, inactive users, and cross-organization requests are denied.
- Privileged cross-organization reads, policy changes, and statement closures write bounded audit events without prompts, responses, API keys, cookies, or secrets.
- This release does not collect money and does not add Stripe, invoices, tax/VAT, refunds, credits, dunning, payment status, multi-currency conversion, manual adjustments, provider-cost passthrough, or dynamic plan pricing.

- 每个组织具有只追加的计费策略历史。现有组织和新组织默认关闭计费，基础费用、包含 Token 和超额费率均为零；本版本不会自行假设商业价格。
- 策略包含 `billing_enabled`、`base_fee_cents`、`included_tokens`、`overage_cents_per_million_tokens`、固定币种 `USD`、UTC 生效月份及单调递增版本。
- 平台管理员仅可通过乐观版本校验和必填原因，为下一个或更晚的 UTC 月份追加策略；禁止本月改价和追溯改价。
- 月度用量只来自不可变且具备组织归属的 `token_usage` 台账；v1 对所有具备组织归属的用量计费，包括平台管理员在该组织上下文内产生的用量；预估不信任浏览器汇总或可变对话内容。
- v1 公式为 `计费Token=max(总Token-包含Token,0)`、`超额费用美分=计费Token*每百万Token费率/1,000,000 四舍五入`、`总费用美分=基础费用+超额费用`；全部采用安全整数运算并保存公式版本。
- 关闭计费的月份返回零预估且不可结账；当前月为预估，未来月份为已排期，已结束月份最多结账一次；v1 不做按天或按比例计费。完全相同的结账请求可幂等重放，预期生效策略版本或已存摘要不一致时冲突。
- 账单固化用量、策略、公式、操作者、原因、周期边界和 SHA-256 摘要，只追加且禁止更新、删除、替换或原地重算。
- 封账后新增的用量不会修改或替换已关闭账单；后续策略只推进 `policy_head_version`，不会改变账单中固化的生效 `policy_version`。
- 企业所有者和组织管理员只能读取本组织；平台管理员可读取任意组织、更新策略和结账。经理、成员、只读、停用用户及跨组织请求均被拒绝。
- 跨组织特权读取、策略变更和结账写入字段有界审计，不记录提示词、回复、API Key、Cookie 或秘密。
- 本版本不收款，也不新增 Stripe、发票、税务/增值税、退款、抵扣、催收、支付状态、多币种换算、人工调账、Provider 成本转嫁或动态套餐定价。

## Data And API / 数据与接口

- Schema v31 adds immutable `organization_billing_policies` and `organization_billing_statements`.
- `GET /api/organization-billing?month=YYYY-MM` returns the authorized caller's monthly projection and any closed statement.
- `GET /api/admin/organizations/:organizationId/billing?month=YYYY-MM` returns the same projection for platform administrators.
- `PUT /api/admin/organizations/:organizationId/billing-policy` accepts exactly `billing_enabled`, `base_fee_cents`, `included_tokens`, `overage_cents_per_million_tokens`, `effective_month`, `expected_version`, and `reason`.
- `POST /api/admin/organizations/:organizationId/billing-statements/close` accepts exactly `period`, `expected_policy_version`, and `reason`.
- Organization directory projections add a lightweight `billing` summary with current-month status, effective policy version, policy head version, enabled state, currency, and allowed actions. Live Token and amount aggregation stays on the dedicated billing endpoint.
- Status values are `disabled`, `scheduled`, `estimated`, `closable`, and `closed`.

## Correctness Invariants / 正确性不变量

1. One organization and UTC month resolve to one effective policy: the latest version whose effective month is not after the requested month.
2. A policy becomes effective no earlier than the next UTC month; no update can reprice the current or an earlier month.
3. A closed statement is byte-stable for the same inputs and cannot change when later Token usage or policies are appended.
4. Cross-organization reads and every unauthorized write fail at the service boundary, not only in the UI.
5. Currency amounts and Token counts remain safe integers; fee multiplication uses `BigInt` and explicit half-up rounding.
6. Statement closure and its audit event commit atomically. Policy append and its audit event also commit atomically.
7. No disabled policy, missing policy, invalid usage row, unsafe integer, clock failure, or digest mismatch is silently converted into a charge.

## Reversible Production Acceptance / 可逆线上验收

1. Upgrade a production-shaped sanitized copy from v30 to v31 twice and verify schema history, integrity, foreign keys, policy backfill, unchanged Token rows, and restore behavior.
2. Record one production organization's exact billing policy, append a uniquely tagged temporary disabled policy for the next month, and verify administrator plus authorized own-organization reads over HTTP.
3. Prove cross-organization and ordinary-member access is denied without exposing another organization's amount or usage.
4. Clone the production database into a root-only isolated acceptance database and perform an actual ended-month statement close there, proving formula, digest, immutability, idempotent replay, audit shape, and zero statement changes in the production database.
5. Append an exact semantic restoration policy through the next version, verify the current projection matches the original effective values, and retain only bounded acceptance/audit evidence.
6. Resolve acceptance through the fixed, dedicated `release-smoke` platform administrator by internal database session only. Never use `derrick`, a historical password, or credential rotation as an acceptance fallback.
7. Before provisioning the dedicated identity, take and verify a separate production backup. Provisioning is create-once and fail-closed: an exact existing identity is reused without changing its credential; any conflicting identity stops the release.
8. Any mandatory failure triggers the recorded database and code rollback before public traffic resumes; login failure is reported and never causes automatic credential recovery.

## Release Boundary / 发布边界

Included: schema v31, append-only policy and statement service, member/admin APIs, compact organization-directory billing controls, current-month estimate, ended-month close, focused migration/calculation/permission/API/UI/release-gate tests, backup, deployment, and reversible production acceptance.

Excluded: payment collection, invoice files or email, tax, multi-currency, refunds, credits, manual adjustment, price catalog mutation, provider-cost accounting, campaign creator settlement, and financial-system integration.
