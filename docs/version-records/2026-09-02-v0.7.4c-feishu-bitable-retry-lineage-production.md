# v0.7.4c Feishu Bitable Retry Lineage Production Record

## Scope / 范围

- Implementation commits / 实现提交: `d2b1f17`, `e949e18`.
- The M4 Feishu panel exposes explicit retry only for a terminal failed Bitable delivery with a known no-write failure code. The selected campaign Owner or organization administrator must supply a 1-280-character reason. / M4 飞书面板仅为已终态失败且属于已知未写入错误的 Bitable 回执提供显式重试；所选活动 Owner 或组织管理员必须填写 1-280 字的重试原因。
- Retry creates a new child outbox delivery from the exact original snapshot and records immutable source/child/actor/reason lineage. It never edits the historical failed receipt and never retries automatically. / 重试会基于精确原始快照创建新的子 Outbox 回执，并记录不可变的源/子/执行者/原因血缘；不会修改历史失败回执，也不会自动重试。
- A pending child remains a manual reconciliation case. A configured-false or provider-failed child refreshes the M4 receipt list and reports the new failed state rather than leaving the source batch selectable. / 待核对子回执仍需人工核对；配置不可用或 Provider 失败的子回执会刷新 M4 回执列表并显示新的失败状态，不会让原失败批次继续可选。
- Replay requires the same actor, UUID, and normalized reason. A changed reason for the same UUID is a conflict. / 重放必须同时匹配执行者、UUID 和规范化原因；同一 UUID 使用不同原因会冲突。
- Schema v9 adds immutable retry lineage. Trusted migration verification and deployment contracts accept managed v9 sources for subsequent deploys and recovery. / schema v9 增加不可变重试血缘；可信迁移验证与部署合同接受已受管 v9 源库，支持后续发布与恢复。
