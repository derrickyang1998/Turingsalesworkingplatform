# v0.7.4b Feishu Reconciliation Console Production Record

## Scope / 范围

- Implementation commit / 实现提交: `7b65140`.
- The current M4 Feishu panel now shows pending Bitable outbox receipts for the selected campaign. A campaign Owner or organization administrator can choose a pending batch, enter one verified unique Record ID per row, and call the existing protected reconciliation endpoint. / M4 当前飞书面板会展示所选活动的待核对 Bitable Outbox 回执。活动 Owner 或组织管理员可选择批次、逐行录入已核验且唯一的 Record ID，并调用既有受保护的对账接口。
- Client-side checks reject an incorrect count, duplicate IDs, or IDs longer than the receipt contract before a network call. Server-side owner/org-admin authorization, pending-only finalization, uniqueness, and immutable terminal receipts remain authoritative. / 客户端在发起网络请求前拒绝数量不符、重复或过长的 ID；服务端 Owner/组织管理员权限、仅待核对状态终态化、唯一性和终态不可变仍是权威约束。
- A per-campaign-and-delivery single-flight lock survives a context switch and a failed manual refresh. A `409` reconciliation response refreshes delivery state so another authorized operator's completed reconciliation is not left as a stale pending panel. / 以活动和批次为维度的单飞锁可跨活动切换和手动刷新失败保留；`409` 对账响应会刷新回执状态，避免其他授权操作员已完成后仍显示陈旧待核对面板。
- No automatic resend, record update, compensation write, or real Feishu Bitable smoke write is included. CSV fallback, Webhook, controlled Bitable creation, and the durable Outbox contract remain unchanged. / 本版本不包含自动重发、记录更新、补偿写入或真实飞书 Bitable 烟测；CSV 兜底、Webhook、受控 Bitable 创建和持久化 Outbox 合同保持不变。
